# 基于开源内核二次开发桌面端自研浏览器深度调研

## 摘要

结论先行：桌面端自研浏览器在 2026 年技术上完全可行，主流且唯一务实的路线是基于 Chromium 分支做“内核跟随 + 外壳与策略差异化”，WebKit/Gecko 只在特定信创或合规场景下才值得评估。制作一个能启动、带自有品牌与默认页的 POC，3～5 人、4～6 周即可（估算）；做到可对外发布的正式版，通常需 12～18 人团队、6～9 个月（估算），首年研发人力成本量级约 1,500万～3,000万元（按一线城市综合人力成本 60万～100万元/人年估算，非公开报价）。真正的成本不在首版，而在长期跟随：Chrome 已于 2026 年 9 月把桌面发布周期从 4 周缩短为 2 周，Chrome 149 与 150 两个版本合计修复 1,072 个漏洞 [2]，下游若做不到 2～4 周内跟版，就等于长期带着 N-day 漏洞运行。

最容易低估的四件事，按踩坑频率排序：一是上游同步（补丁越深、rebase 越痛，改 `content/` 与 `blink/` 的代价是改 `chrome/browser/` 的数倍）；二是自动更新与签名链路（Windows 签名、macOS Developer ID 公证、信创 deb/rpm 仓库是三套完全不同的工程）；三是国密与信创适配要动 `net/` 的 TLS 层，属于高风险区；四是生态壁垒——扩展商店、账号同步、Widevine/编解码器都不在开源 Chromium 里，需要自建或商业授权。

本报告所有命令基于 Chromium 主干通用工具链（depot_tools / gclient / gn / ninja），版本号口径为 2026 年 11 月；凡标注“估算”的数字均为基于公开团队规模与发布节奏推算，非厂商披露。

## 一、结论先行与关键数字

这一章给决策者一个可直接拍板的判断框架：能不能做、要多少人多少钱、什么时候会疼。读完你应该能回答“我们该不该开这个项目”，以及“如果开，第一笔预算该批多少”。

### 一句话判断

可行，但它的本质不是“做浏览器”，而是“长期维护一个 Chromium 下游分支”。Chromium 官方代码规模在千万行量级，Google 巅峰期投入超过 1,000 名工程师，按当时湾区薪资估算十年研发成本约 30 亿美元 [5]；今天没有任何单一企业能从零重建同等能力，微软也在 2020 年放弃 EdgeHTML 转投 Chromium [5]。所以“自研”的现实定义是：在上游之上持有可控的差异化补丁集，并以不慢于上游安全节奏的频率发版。

### 关键数字一览

表1：首版可控、长期维护才是成本主体（除注明外均为估算）

| 项目 | 量级 | 口径说明 |
|---|---|---|
| POC 团队 | 3～5 人 / 4～6 周 | 构建工程师 1～2、C++ 2、测试 1 |
| 正式版团队 | 12～18 人 | 内核 4、构建 2、UI/前端 3、测试 3、安全 1～2、发布 1～2 |
| 首版周期 | 6～9 个月 | POC→内测→公测→正式版，不含信创多架构 |
| 首年人力成本 | 1,500万～3,000万元 | 12～18 人 × 60万～100万元/人年 |
| 每次上游跟版 | 2～4 周 / 6～10 人 | Chrome 已改为双周发布 [2] |
| 源码与构建磁盘 | 源码 30～60GB，构建目录 20～80GB/目标平台 | 随 `is_component_build`、符号等级变化 |
| 全量编译耗时 | 高配 32 核机器 30～90 分钟；增量 1～5 分钟 | 估算，依赖 `use_jumbo_build` 与缓存 |
| 安装包体积 | Windows 约 120～180MB，macOS 约 180～250MB | 含多架构与资源包，估算 |

这些数字的说服力来自对照而非精确：Brave 主要版本约每 3 周更新一次 [4]，国内主流双核浏览器“一年至少两次升核”，360 对中危以上漏洞按周级发版 [6]。也就是说，行业内“合格下游”的门槛是月度跟版、周级应急补丁；低于这个节奏的产品，在安全口径上就不算自研内核，只算旧版封装。

### 四个最容易低估的风险

第一是上游同步的复利效应。补丁数量本身不可怕，可怕的是补丁落在上游频繁改动的文件上。`chrome/browser/` 下的品牌、首跑页、默认搜索改动通常冲突率低；一旦碰 `net/` 的 TLS 握手、`content/` 的进程模型或 `blink/` 的渲染管线，每个上游大版本都要重新验证，冲突解决成本呈非线性上升。第二是发版工程：Windows Authenticode、macOS Developer ID 签名加公证（自 2023年11月1日起必须用 notarytool 或 Xcode 14 以上，altool 已被拒绝）、信创 deb/rpm 仓库与 GPG 签名，是三条独立流水线 [7]。第三是国密：SM2 双证书体系要改 BORINGSSL/`net/` 的加密套件协商，属于最深的改造层，且必须跟随上游 BoringSSL 升级重做 [8]。第四是人才：能独立解决 Chromium 链接期与 Mojo IPC 问题的人极少，招聘周期常按季度计（经验判断）。

## 二、路线地图：三内核取舍与套壳边界

这一章解决“选哪条内核路线”的问题。读完你能给出一张选型表，并能清楚向老板解释为什么桌面端实际只剩 Chromium 一个理性选项，以及 CEF/Electron 为什么不算同一件事。

### 三条路线的真实桌面格局

Chromium（含 Blink + V8）是唯一同时覆盖 Windows、macOS、Linux/信创、且标准支持与网页兼容位于第一梯队的开源底座。Chrome、Edge、Brave、Vivaldi、Opera 以及国内 360、QQ、搜狗、龙芯浏览器、红莲花等桌面产品均属这一阵营；连 Firefox 的对手 Microsoft 都已转投 [5]。其代价是代码体量巨大、模块“可拆性”差——有长期从事内核开发的工程人士指出，Chromium 很多功能没有编译开关可关，想裁掉只能手动删代码，而 WebKit 相反，连 SVG 这类小功能都有宏可关 [5]。这句话基本概括了 Chromium 与 WebKit 的工程哲学差异。

WebKit 在桌面端只剩两条现实分支：Apple 平台的 WKWebView/Safari（不可用于第三方桌面浏览器外壳），以及 Linux 上的 WebKitGTK（LGPL/LGPLv2+，Midori 等轻量浏览器使用）[9]。WebKitGTK 的优势是体积小、可裁剪、LGPL 对闭源分发友好；劣势是网页兼容面窄于 Blink、Windows 支持弱、国内政企站点与 ActiveX/NPAPI 遗留适配基本无人维护。除非你的目标平台锁定信创 Linux 且只跑内网固定 Web 应用，否则不建议作为主线。

Gecko 是 MPL 2.0 的文件级 copyleft，对修改 Gecko 源文件要求以 MPL 开源，新增独立文件可闭源 [9]。桌面二次开发的现实路径是基于 Firefox ESR 做定制（ ESR 分支提供长周期安全支持），典型场景是隐私导向或强合规定制。问题是：国内政企站点对 Gecko 的兼容测试投入几乎为零，国密与信创生态几乎全部围绕 Chromium 构建，且 ESR 之外跟随主线等价于自建 Firefox。因此 Gecko 适合“隐私品牌 + 欧美市场”，不适合“国内桌面 + 信创”。

表2：桌面端三内核路线对比（2026年口径）

| 维度 | Chromium | WebKitGTK | Gecko/Firefox ESR |
|---|---|---|---|
| Win/macOS/Linux 覆盖 | 全平台一等公民 | Linux 强，Win 弱 | Win/mac/Linux 可用 |
| 网页兼容与标准 | 第一梯队 | 次之 | 次之，国内站点风险高 |
| 主许可证 | BSD 风格 + 多许可证 third_party | LGPLv2+ | MPL 2.0 文件级 copyleft |
| 桌面代表产品 | Chrome/Edge/Brave/Vivaldi/360 | Midori | Firefox ESR 定制版 |
| 国密与信创生态 | 成熟，多家厂商已适配 | 几乎空白 | 几乎空白 |
| 裁剪体积 | 难裁，体积大 | 易裁，体积小 | 中等 |
| 推荐度（桌面通用） | 首选 | 仅信创内网专用 | 仅隐私/海外细分 |

### 与 CEF / Electron / 系统 WebView 的边界

这三条不是“轻量版内核二次开发”，而是把 Chromium 当库用：CEF 提供的是已封装好的浏览器进程与 API，你写的是宿主程序；Electron 把 Node 与 Chromium 绑在一起，主进程是 JS；系统 WebView（WKWebView / WebView2）直接复用操作系统自带的引擎，连内核升级都不归你管。它们的共同点是：你无法控制渲染进程策略、无法定制网络栈与国密、无法持有内核版本节奏，因而无法满足“自研内核 + 可信升级 + 国密信创”的诉求。反过来，如果你的真实需求只是“一个带固定入口的桌面客户端”，CEF/WebView2 的成本低一个数量级，强行上 Chromium 分支是浪费。第九章给出量化判据。

一个值得一线开发者关注的中间形态是 OpenAI Atlas 的 OWL 架构：把 Chromium 浏览器进程作为独立服务运行在宿主应用之外，主界面用 SwiftUI/AppKit 自建，二者通过 Mojo IPC 通信，并为 Mojo 写了 Swift/TypeScript 绑定 [3]。这说明“自研 UI + 上游内核进程”是当下高端桌面浏览器的事实标准形态，也说明即便强如 OpenAI，也要承担“Chromium 跟进 + 多平台兼容 + 凭证管理 + 企业治理”的硬成本 [3]。

## 三、Chromium 架构与改造面

这一章把 Chromium 拆成“能碰 / 慎碰 / 别碰”三层，并给出上游同步的工程纪律。读完你能对着目录树判断每个需求该落在哪一层，以及这个改动将来 rebase 会有多痛。

### 分层与关键目录

Chromium 的桌面形态是自底向上的五层：最底是 `base/`、`third_party/`（BoringSSL、Skia、FFmpeg、ICU 等）；往上是 `v8/`（JS 引擎，含 JIT、GC、快照）与 `third_party/blink/`（DOM/CSS/布局，架构上被当作第三方库对待 [5]）；再往上是 `net/`（DNS、Cookie、HTTP/QUIC、TLS、代理、缓存）；然后是 `content/`（多进程框架、渲染/浏览器/GPU/网络服务进程、导航与历史栈的公共层）；最上层才是 `chrome/`（真正的“Chrome 浏览器产品”：`chrome/browser/`、`chrome/app/`、Views UI、WebUI 设置页、安装器与更新器）[5]。另有两个横切目录：`ui/`（Views 控件与主题、资源）、`mojo/`（IPC 接口定义与绑定生成）。

这个分层的工程含义非常直接：你的差异化 90% 应该落在 `chrome/` 与 `ui/`，这是上游为下游预留的“产品层”；`content/` 是公共嵌入层，改动要克制并尽量以 `content::ContentBrowserClient` 等接口扩展点实现，而非改实现；`net/`、`v8/`、`blink/`、`base/` 属于“只有非改不可时才改”的区域，每改一处都要登记为高冲突补丁。

表3：关键目录、典型改造与冲突风险

| 目录 | 职责 | 典型改造 | rebase 风险 |
|---|---|---|---|
| `chrome/app/` | 入口、资源 ID、版本信息 | 品牌名、图标、about 页 | 低 |
| `chrome/browser/` | 产品逻辑、首跑、默认搜索 | 启动页、策略、默认引擎 | 低～中 |
| `chrome/installer/` | 安装包与更新器 | MSI/DMG/deb/rpm、更新 URL | 中 |
| `ui/` `ui/views/` | 控件、主题、资源包 | 自研界面、深色主题 | 中 |
| `content/` | 多进程与导航公共层 | 进程模型、自定义 Mojo 服务 | 高 |
| `net/` | 网络栈与 TLS | 国密 SM2、证书校验、代理审计 | 高 |
| `third_party/blink/` | 渲染与 Web 平台 | 内核级特性、指纹防护 | 极高 |
| `v8/` | JS 引擎 | 几乎不改，只跟升级 | 极高 |
| `sandbox/` `services/` | 沙箱与系统服务 | 信创低内核降级、权限收敛 | 高 |

### 能改、慎改、别碰的判断准则

能改的判据是“上游是否已经提供扩展点”：品牌走 `chrome/app/` 的资源与 `generated_resources.grd` / `chrome_resources.grd`；默认搜索走 `TemplateURLService` 的预置数据（`chrome/browser/search_engines/`）与首跑 pref；策略走 `chrome/browser/policy/` 的 policy schema（JSON 定义）+ 平台 provider；这些都有稳定接口，冲突率低。慎改的是 `content/` 与 `net/`：能用 `ContentBrowserClient`、`WebContentsDelegate`、`URLRequestInterceptor`（或 `NetworkService` 拦截）实现的，不要下沉到实现文件。别碰的是 `v8/` 与 `blink/` 的实现细节——除非你要做的是真正的引擎创新，否则任何收益都抵不过每次升级的冲突成本；指纹防护、广告拦截这类需求应优先用 `ContentBrowserClient` 与 declarativeNetRequest 语义在浏览器层实现，Brave 的 Shields 正是这个思路 [4]。

### 上游同步策略：补丁集治理比写代码更重要

推荐的主干模型是“上游分支只读 + 自有补丁分层”：维护 `upstream/<major>` 分支严格镜像 `branch-heads/<major>`，自有改动放在 `downstream/<major>`，且按“品牌资源层 / 产品逻辑层 / 网络与内核层”拆成独立提交序列，便于 rebase 时逐层丢弃或重放。每次跟版固定动作：`git fetch origin` → 检出新 `branch-heads/<M>` → `gclient sync --with_branch_heads --with_tags` → `git rebase upstream/<M> downstream/<M>` → 逐冲突解决 → 全平台构建 → 安全补丁回归套件 → 灰度。

Brave 的做法值得抄：自有客户端代码用 MPL-2.0 独立成库，与 Chromium 补丁物理隔离，主要版本约每 3 周发布一次 [4]；这种“上游补丁最小化 + 差异化代码外置”的结构，使 rebase 冲突集中在极少数文件。反面案例是停留在 Chromium 49 的产品——因为上游 49 之后停止支持 Windows XP，长期停版导致 WebAssembly、WebGL 2.0 支持缺失并积累大量未修 0day [6]。结论：补丁行数不是核心指标，**补丁落点**才是；把改动压在 `chrome/` 与 `ui/`，跟版成本可以控制在 2 人周/版本量级（估算），落进 `net/`/`blink/` 则会放大到 4～8 人周甚至更多（估算）。

## 四、从零到可运行：完整操作链路

这一章是全文最偏手写的部分：从空目录到签名安装包加自动更新，给出可复制的命令与每一步的坑。读完你应该能在一周内让团队每个人的机器都编出可启动的自研浏览器。

### 环境准备（三平台差异）

共用前置：Git、Python 3（depot_tools 自带）、约 150GB 可用磁盘（源码 + 至少两个目标平台的构建目录）、16GB 内存起步（推荐 32GB 以上，16GB 编 Debug 极易 OOM）。depot_tools 必须放在 PATH 最前，否则 `gcl` 会命中系统的 GNU Common Lisp。

Windows：Visual Studio 2022（含“使用 C++ 的桌面开发”，版本需与所跟 Chromium 分支的官方要求一致，升级 VS 常导致旧分支编不过，建议用固定版本镜像）、对应 Windows SDK、启用长路径支持与 NTFS 大小写敏感（可选但推荐）。macOS：Xcode 版本同样与分支强绑定，装 Command Line Tools，区分 x64 与 arm64 产物（推荐 `target_cpu="arm64"` 主构建 + universal 合并）。Linux/信创：安装官方 `install-build-deps.sh`，UOS/麒麟基于 Debian/Ubuntu 或 RPM 系，需注意系统 clang/gcc 版本往往低于上游要求，通常用 Chromium 自带 sysroot 或自建 toolchain 容器。

```bash
# 1. 获取 depot_tools（三平台通用，Windows 用同仓库的 bat）
git clone https://chromium.googlesource.com/chromium/tools/depot_tools.git "$HOME/depot_tools"
export PATH="$HOME/depot_tools:$PATH"          # 必须置顶
export DEPOT_TOOLS_UPDATE=1

# 2. 拉取源码（推荐钉死分支，而不是 main）
mkdir -p ~/chromium && cd ~/chromium
fetch --nohooks chromium --no-history          # 只取当前快照，省时省盘
cd src
git checkout -b downstream/M refs/remotes/branch-heads/M   # M 为目标稳定大版本
gclient sync --with_branch_heads --with_tags -j 8
gclient runhooks

# 3. 配置构建目录
gn gen out/Release --args='is_debug=false is_component_build=false symbol_level=1 blink_symbol_level=0 use_jumbo_build=true target_cpu="x64"'
gn args out/Release --list          # 查全部可用参数及说明
gn desc out/Release //chrome:chrome deps   # 查依赖，排查“为什么编了这么多”
```

`--no-history` 与 `-j 8` 能把首次同步从数小时压到数十分钟（估算，依赖出口带宽）；但注意 `--no-history` 后无法直接 rebase，正式分支开发应保留完整历史或在 CI 上另做镜像。`is_component_build=true` 链接快、适合日常开发但产物是一堆 dll/so，不能用于发布；发布用 `false`。`symbol_level=0` 体积最小但线上崩溃无法符号化，推荐 `1` 并把 debug 文件单独归档到符号服务器。

### 编译、运行与调试

```bash
# 4. 编译（只编浏览器主目标，别编 chrome 全家桶）
ninja -C out/Release chrome
ninja -C out/Release chrome resources.pak chrome_100_percent.pak chrome_200_percent.pak
# Windows 安装包目标：mini_installer；macOS：chrome；Linux：chrome + chrome_sandbox

# 5. 运行与常用调试开关
out/Release/chrome --no-first-run --user-data-dir=/tmp/myprofile --enable-logging=stderr --v=1
out/Release/chrome --remote-debugging-port=9222      # 用 CDP 调页面与 DevTools
# Windows: 用 vscode 的 cppvsdbg 附加 chrome.exe；Linux/macOS: lldb -p <pid>，或 gdb --args
# 多进程调试关键：在 browser 进程设 follow-fork-mode / 直接对 renderer 进程 attach
# 渲染问题先看 chrome://gpu、chrome://tracing（categories: cc,blink,disabled-by-default-devtools.timeline）
```

调试的真实难点在多进程：断点默认只命中 browser 进程，renderer/GPU/utility 进程需按 `--renderer-process-limit=1` 或 `--single-process`（仅调试用，语义与生产不同）收敛后再 attach。Mojo 接口问题用 `--enable-logging=stderr --vmodule=*mojo*=2`，网络问题用 `net-log` 与 `chrome://net-export`。日常开发强烈建议开 `is_component_build=true symbol_level=2 is_debug=true` 的 `out/Debug`，改 `chrome/browser/` 单文件增量编译通常 1～5 分钟（估算）。

### 测试与静态检查

```bash
ninja -C out/Release unit_tests browser_tests     # 上游测试套件，跟版必跑
out/Release/browser_tests --gtest_filter=FirstRun*=   # 只跑自有改造相关用例
git cl format                      # clang-format，提交前必跑
gn format BUILD.gn                 # GN 文件格式化
# CI 建议：每个下游提交跑 presubmit（git cl presubmit）+ 三平台编译 + 冒烟用例
```

### 打包、签名与公证

Windows：上游 `mini_installer` 产出 EXE 安装包，企业分发需 EV/OV Authenticode 签名（`signtool sign /fd SHA256 /tr <时间戳服务器> /td SHA256`），若要上架 Microsoft Store 需按 MSIX/Store 签名流程并过认证；驱动级组件（如有自研过滤驱动）另需 WHQL/EV 内核签名，成本与周期远高于应用签名。macOS：产出 `.app` 后用 `codesign --deep --force --options runtime --sign "Developer ID Application: ..."` 签名，打 DMG/PKG 后用 `xcrun notarytool submit ... --wait` 公证并 `xcrun stapler staple`，否则 Gatekeeper 会拦截；自 2023年11月1日起 altool 与 Xcode 13 及更早版本上传已被拒绝 [7]。信创 Linux：deb（UOS/深度系）与 rpm（麒麟系）双包，system-wide 安装需处理 `chrome_sandbox` 的 setuid 或改用 user namespace 沙箱；低内核（<3.8 无 user namespace）只能退回 setuid sandbox，且 seccomp-BPF 需内核 ≥3.5，这是信创低版本内核上最常见的“No usable sandbox”致命错 [1]。仓库需 GPG 签名并适配统信/麒麟应用商店的上架审核与签名要求。

### 自动更新

上游 `chrome/installer/` 的更新器（Windows 的 Google Update 体系、macOS 的 Keystone）与 Google 域名强绑定，下游通常自建：Windows 用自研更新服务或现成更新框架，走 HTTPS 清单文件（版本、差分补丁、SHA256、签名），后台服务静默下载、下次启动生效；macOS 自建 Sparkle 类更新或自行实现拖拽替换 + 公证校验；Linux/信创走自有 apt/yum 仓库 + 定时检查。更新包必须二次签名并在更新器内校验，否则更新通道本身就是供应链攻击面。Chrome 正在研发“动态补丁”（免重启更新），并已在 macOS 优化安装体验 [2]，下游短期难以跟进，需接受“重启生效”的现实。

## 五、常见差异化功能的实现切入层

这一章把产品需求逐条映射到代码层，并标出哪些能用配置解决、哪些必须写 C++。读完你能给产品经理一份“这个需求要几个人天、落在哪个目录”的估算表。

### 品牌、资源与启动页

品牌替换的最小集合：`chrome/app/` 的产品名与版本资源（`chrome/app/chrome_exe.ver`、`product_config.json` 或 grd 中的 IDS_PRODUCT_NAME）、图标（各平台 `.ico/.icns/.png` 与 `chrome/app/theme/`）、`about` 页与 `chrome://credits`。注意 `chrome/browser/resources/` 下的 WebUI 里仍散落品牌字符串，需全局搜索替换并跑 `chrome://chrome-urls` 逐页目检。启动页有两条路：轻量的用 `--app` + 首跑 NTP 覆盖（`FirstRunService`、`chrome/browser/first_run/`），重的自建 WebUI（`chrome/browser/resources/` 加 Mojo 接口）或直接用 `WebContents` 加载本地 NTP。前者一天可完成，后者需 1～2 人周并要处理进程生命周期与崩溃恢复（估算）。红线：不得使用 Chrome/Chromium 商标与近似配色做误导性宣传，BSD 条款明确禁止未经书面许可用 Google 或其贡献者名义背书推广产品 [10]。

### 默认搜索引擎、主页与首跑配置

默认引擎不用改代码逻辑，改数据：`chrome/browser/search_engines/` 中的预置 TemplateURL（`prepopulated_engines.json` 及生成逻辑），把自有引擎设为 `default`，并确认 `DefaultSearchProviderEnabled` 策略不被覆盖。首跑行为通过 `Local State`/`Preferences` 的默认 pref（注册于 `chrome/common/pref_names.cc` 与各 `RegisterProfilePrefs`）设定：首页、是否显示首次运行对话框、是否导入其他浏览器数据、是否询问设默认浏览器。企业批量部署则走策略而非改代码（见下）。经验坑：默认搜索在部分市场受“选择屏”与地区规则约束，直接硬编码可能被上游后续版本的选择逻辑覆盖，跟版时要回归这一项。

### 企业策略与管控

Chromium 的策略系统是最省事的差异化入口：在 `chrome/browser/policy/` 的 `policy_templates.json`（或新版本的 schema 体系）里新增自有策略，生成 JSON schema 与文档，平台 provider 自动生效。Windows 走注册表 `HKLM\SOFTWARE\Policies\<Product>`，macOS 走 `/Library/Managed Preferences/<bundle_id>.plist`（含 `managed` 子字典），Linux/信创走 `/etc/opt/chrome/policies/managed/*.json`（自有产品替换为自家路径）。常用内置策略直接复用：`HomepageLocation`、`DefaultSearchProviderEnabled/DefaultSearchProviderSearchURL`、`ExtensionInstallForcelist/Blocklist`、`URLBlocklist`、`DeveloperToolsAvailability`、`IncognitoModeAvailability`。政企场景建议把“策略下发”做成自研管理端 + 签名策略包，客户端校验签名后落盘，避免本地策略被篡改——已有研究显示攻击者可通过伪造 Preferences/Secure Preferences 的 HMAC 静默注册恶意扩展并绕过扩展策略 [11]，这说明策略与 pref 完整性本身是攻击面，自研产品必须把 `Secure Preferences` 的种子与校验纳入自有安全设计。

### 账号与同步

Chromium 开源版不含 Google 账号与同步实现（同步依赖闭源组件），这是下游最常踩的空坑。三条路：一是自建轻量同步（书签/历史/密码/打开标签页），复用 `sync/` 的数据模型但替换 `SyncService` 的后端为自有 HTTPS/WebSocket 服务，密码必须用本地主密钥加密后再上传（参考 Brave Sync Chain 用 32 字节种子 + BIP39 助记词、客户端加密、服务端只见设备元信息的做法 [4]）；二是不做同步，只做企业目录（LDAP/OAuth2）登录 + 策略下发，成本最低，政企项目多走这条；三是采购第三方同步组件。自研全量同步是 3～6 人月的独立工程（估算），且密码同步一旦出事是重大数据事件，建议首版只做书签与设置同步。

### 扩展体系

`chrome/browser/extensions/`、`extensions/` 与 Chrome Web Store 的客户端接口是开源的，但商店本身不是。可选：对接 Chrome Web Store（需与 Google 协商，且扩展的 API 兼容性要测）、自建扩展商店（签名与更新走自有 CRX 分发、`ExtensionInstallForcelist` 指向自有更新 URL）、或只支持企业强制安装的白名单扩展。自研商店的成本不在客户端而在审核与签名体系；政企场景通常只需“白名单 + 强制安装 + 版本锁定”，用内置策略即可覆盖 [11]。

### 安全沙箱

默认保留上游沙箱，不要为了“能跑”全局加 `--no-sandbox`——这是国内定制浏览器最常见也最致命的偷懒。信创低内核场景的正确做法是按内核能力选择 user namespace 或 setuid sandbox，并确认 seccomp-BPF 生效 [1]；GPU 进程在国产显卡驱动上常需加白名单而非关沙箱。若要做“内网隔离”（只允许访问白名单域、禁用外网、强制代理），实现点在 `net/` 的 `URLRequest` 拦截与 `ProxyConfigService`、以及 `content::ContentBrowserClient::WillCreateURLLoaderFactory` 自定义 factory，配合策略下发，比改 `net/` 实现安全得多。

### 国密与证书适配

国密是唯一必须下沉到 `net/` 的常见需求，也是 rebase 成本最高的改造。切入层是 `net/ssl/` 的 SSLClientSocket（基于 BORINGSSL，位于 `third_party/boringssl/`）：替换为支持 SM2/SM3/SM4 与双证书体系的 TLS 实现（业界常用 Tongsuo/BabaSSL 一类分支），在 ClientHello 协商与证书校验处增加国密套件优先、国密根证书库（独立于系统 NSS/Keychain）、以及 SM2 客户端证书（UKey/密码模块通过 PKCS#11 或厂商 SDK 接入）。同时要在证书错误页与 `chrome://net-internals` 增加国密错误码，在 `net/cert/` 增加国密信任锚管理。行业实践显示国密浏览器普遍以“加密套件层同时支持 RSA/ECC/SM2 并自适应”为基线，并以“及时升级到最新 Chromium 安全内核”为前提 [8]；国内已有产品以密码模块形式取得国密局产品型号证书并适配龙芯、飞腾、兆芯、鲲鹏及 UOS/银河麒麟 [12]。这意味着：如果你的客户要求商密型号证书，改造要连密码模块合规一起做，不是改几行 TLS 代码就完事。建议把国密实现做成独立动态库 + `net/` 内最小适配层，升级时只需重做适配层。

### 内网隔离与审计

审计日志走浏览器层的事件收集（导航、下载、扩展安装、策略命中、策略违规），经 Mojo 上报到 browser 进程的审计服务，签名后批量回传管理端，本地留存加密。关键点：不要在 renderer 里做审计（可被页面侧信道干扰），不要在 `net/` 里逐包抓（性能与合规双输）。下载隔离、外发管控用 `DownloadManagerDelegate` 与 `URLRequest` 拦截实现；剪贴板/打印/截屏管控用策略 + Views 层禁用。

## 六、信创 Linux 适配差异单列

这一章单独讲 UOS/麒麟与 Windows/macOS 的工程差异，因为这些差异往往在 POC 阶段被忽略、在公测阶段集中爆炸。读完你能列出信创适配的独立工作包与验收标准。

### 与 Win/mac 的三类根本差异

第一类是工具链与架构：信创侧要同时覆盖 x86_64（兆芯、海光）与 ARM64（飞腾、鲲鹏），部分项目还要龙芯 LoongArch（上游对 LoongArch 的支持成熟度随版本变化，常需自备补丁）。每个架构都是一套独立构建目录与产物，CI 矩阵从 2 变成 5～6，构建机与缓存成本翻倍以上（估算）。第二类是系统库与内核：UOS/麒麟的基础库版本、glibc、GTK/Atspi、字体与输入法框架与上游 Ubuntu 不一致，音视频编解码依赖系统库时经常缺失；内核版本偏低直接影响沙箱可用性（user namespace 需 ≥3.8、seccomp-BPF 需 ≥3.5）[1]。第三类是分发与合规：deb 与 rpm 双包、系统应用商店上架审核、仓库 GPG 签名、以及政府采购对“预装浏览器与操作系统同一厂商、提供浏览器软件著作权登记证书”的硬性条款——已有政府采购参数明确要求“操作系统软件需预装原厂浏览器而非第三方浏览器，操作系统与预装浏览器需由一个厂商提供” [13]。这条对第三方浏览器厂商是结构性壁垒：你很难进“预装”，只能进“应用商店可选安装”或项目定制采购。

### 信创生态现状与可借鉴对象

信创侧已形成较成熟的 Chromium 下游群：龙芯浏览器基于 Chromium 开发，支持国家商用密码算法模块与国产安全协议模块，兼容龙芯/鲲鹏/兆芯/飞腾及 UOS、银河麒麟；红莲花安全浏览器以密码模块形式取得国密局产品型号证书并适配多款国产 CPU 与 OS；360 安全浏览器在信创商店提供国密套件与完整信创迁移方案 [12]。这些产品的共同点是“Chromium 版本 + 国密模块 + 管理端”三件套，差异化在管理端与密码资质，而非 UI。对你的启示：信创项目的胜负手是资质（商密型号、软著、适配认证清单）与项目交付能力，不是浏览器功能炫技。

### 信创适配工作包与验收标准

### 成本模型：首版是一次性支出，跟版是永续支出

持续成本可用一个简单公式估算：每上游大版本成本 = rebase 冲突解决（补丁落点决定，2～8 人周）+ 三平台全量构建与安装包回归（1～2 人周）+ 安全补丁回归与灰度（1 人周）+ 信创多架构额外验证（1～2 人周）。Chrome 自 2026年9月起桌面双周发布 [2]，一年约 26 个版本；下游不可能每个都跟，现实策略是“跟随 Stable 大版本（约每 4 周取一次基线）+ 高危 0day 走热补丁分支”，即每年约 12 次大跟版 + 若干次应急。按每次 4～6 人周、6～10 人参与计算，年维护人力约 6～10 人常驻（估算），这正是表6“持续维护”列的含义。换句话说：首版之后你并没有“项目结束”，而是转入一支永久的 10 人级平台团队。Brave 约每 3 周发一次主版本 [4]、360 对中危以上漏洞按周级发版 [6]，都是这一成本结构的公开佐证。

### 性能、体积与维护成本的实际坑

体积：默认 GN 产物远大于 Chrome 发布版，因为发布版启用了官方品牌的压缩资源、专有编解码与链接优化；下游需逐项评估 `symbol_level`、`use_jumbo_build`、资源 pak 精简、以及是否裁剪不用组件（翻译、Google 服务相关在开源版本就不全），但如前文所述 Chromium 裁剪困难，别把“瘦到 80MB”写进 KPI。性能：常出问题的是自研启动页同步加载远端资源阻塞首帧、审计日志同步写盘卡 UI 线程、国密握手未走异步导致首屏变慢——三条都要求改造走异步与 Mojo，别在 UI 线程做 IO。内存：多进程模型本身带来较高常驻内存，自研服务进程要能按需启动。维护：最贵的是“无人记得为什么改这行”，每个补丁必须带上游对应 CL 链接、改造理由、回归用例编号，否则一年后没人敢 rebase。

## 八、合规与生态

这一章把许可证义务、商标红线、隐私合规、信创资质与三平台分发要求讲清。读完你能产出一份法务可直接签核的合规清单，避免红芯式的舆论与法律风险。

### 各层许可证与开源义务

Chromium 主体是 BSD 风格许可证：源码再分发须保留著作权声明、条件列表与免责声明，二进制再分发须在文档或随附材料中复制上述声明，且未经书面许可不得用 Google 或贡献者名义背书推广 [10]。`third_party/` 是混合许可证池：Blink 随 Chromium 主体、V8 为 BSD 风格、Skia 为 BSD、ICU 为 ICU 许可证、FFmpeg 在开启 H.264/AAC 等时引入 GPL 相关组件（这也是开源 Chromium 不带专有编解码的原因之一）、BoringSSL 为 BSD/ISC 类。WebKitGTK 为 LGPLv2+，动态链接下闭源分发可行但需提供替换库的能力与许可证文本 [9]；Gecko 为 MPL 2.0，修改过的 MPL 文件必须以 MPL 开源，新增独立文件可闭源，动态链接更利于合规 [9]。

实操上要做三件事：一是生成 SBOM 与 NOTICE 清单（上游 `chrome/common/credits` 与 `about:credits` 是现成来源），安装包内附完整许可证与源码获取地址；二是把自有修改文件与上游文件物理分离（Brave 用 MPL 独立库的做法可借鉴 [4]），避免“修改即被传染”的争议；三是专有编解码（H.264/H.265/AAC）、Widevine DRM 需单独商业授权，开源版默认缺失，这直接影响视频站点可用性，必须在售前说清。

### 商标与品牌红线

BSD 条款禁止用 Google 名义背书 [10]；Chromium 名称与图标同样有商标约束，下游应使用自有名称与图标，在“关于”页显著标注“基于 Chromium 开源项目（版本号）”，不得宣称“自研内核”暗示从零实现引擎。红芯事件的教训正是：使用开源代码本身不违规，违规的是未披露来源并宣称“世界第五颗自主内核”，最终公开致歉并承诺显著标注 [10]。国内政企宣传中“自主可控”可以讲（补丁自主、构建自主、升级自主、密码模块自主），“自主研发内核”要慎之又慎。

### 隐私与数据合规

下游浏览器默认会带遥测、崩溃上报、安全浏览（URL 黑名单查询）、拼写检查、翻译等外发行为，在《个人信息保护法》与等保场景下必须逐项审计并给出开关：默认关闭非必要外发、上报数据最小化与去标识化、提供隐私政策与撤回入口、企业版支持完全离线（禁用 Safe Browsing 在线查询、组件更新走内网镜像）。账号与同步数据按敏感个人信息处理，密码同步需端侧加密且服务端不可见（Brave Sync Chain 的客户端加密模型是 good practice [4]）。审计日志本身也是个人信息集合，需明确留存期与访问控制。

### 信创目录、商密与国产化要求

信创侧要过三关：操作系统适配认证（UOS/银河麒麟等出具兼容认证）、软硬件目录与采购参数（如“预装原厂浏览器、同一厂商、提供软著证书”类条款 [13]）、以及涉密/商密场景的密码产品资质（国密局商密型号证书，红莲花已完成 [12]）。此外软著登记、等保测评、供应链安全（构建机与签名私钥的物理隔离、可复现构建）都是政企项目常见硬性项。时间上，适配认证通常数周到数月、商密资质以季度计（经验判断），应作为关键路径单列，不能压在研发里程碑里。

### 三平台分发与签名差异

| 维度 | Windows | macOS | 信创 Linux |
|---|---|---|---|

## 九、竞品格局与可借鉴点

这一章按“差异化来自哪里”而不是按品牌罗列竞品，让你看清哪些护城河可复制、哪些是坑。读完你能为自己的产品选一个不与客户正面撞车的定位。

### 国际阵营：四种差异化范式

Chrome/Edge 代表“上游本身 + 生态捆绑”，Edge 还证明大厂也会放弃自研引擎转投 Chromium [5]，其可借鉴的是企业策略与更新工程，不可复制的是分发渠道。Brave 代表“隐私默认 + 自研广告/搜索经济”，Shields 在浏览器层做拦截、自研同步用助记种子客户端加密、主版本约每 3 周跟随上游、自有代码 MPL-2.0 [4]；可借鉴的是补丁分层与同步模型，需避开的是广告与代币模型在国内政企场景基本不可用。Vivaldi 代表“UI 即产品”：在 Chromium 之上自建大量 Views/WebUI 界面（标签堆叠、工作台、笔记、邮件日历），证明“深度改 UI 不改引擎”是差异化性价比最高的路线；风险是 UI 改动量大、每次上游 UI 重构都要跟随。Opera 代表“功能聚合 + 侧边栏服务”，可借鉴轻量化与流量入口设计，需避开捆绑推广带来的信任损耗。OpenAI Atlas 代表“Agent 原生 + 内核服务化”，用 OWL 把 Chromium 浏览器进程拆到主应用之外、Mojo 通信、SwiftUI 自建界面 [3]；但它同时承担浏览器与 Agent 平台双重固定成本，且 Agent 提示注入防御是“没有终点的开支” [3]，中小团队不宜在首版跟进。

### 国内阵营：双核、国密与信创三条线

360、QQ、搜狗等桌面产品历史上多为“Chromium + 兼容 IE 的双核”形态，行业人士指出国内 360、UC、QQ、搜狗桌面端普遍基于 Chromium 或其 Blink/WebKit 引擎，并保持一年至少两次升核 [6]；可借鉴的是双核兼容与快速升核的工程纪律，需避开的是长期停在 Chromium 49 一类老基线导致的标准缺失与 0day 堆积 [6]。信创线以龙芯浏览器、红莲花安全浏览器、360 信创版为代表，差异化在国密模块、管理端与适配清单 [12]，可借鉴“内核 + 密码模块 + 管理端”三件套的产品结构。需明确避开的坑是红芯式宣传翻车 [10]，以及“套壳冒充内核”在政企验收与安全测评中的失信风险。

表9：竞品差异化范式与可借鉴/需避开

| 产品 | 差异化核心 | 可借鉴 | 需避开 |
|---|---|---|---|
| Edge | 企业策略与更新工程 | 策略体系、灰度发布 | 渠道捆绑不可复制 |
| Brave | 隐私默认、自研同步与搜索 | 补丁分层、客户端加密同步 | 广告/代币模型 |
| Vivaldi | 深度自研 UI | Views/WebUI 差异化 | UI 跟随成本 |
| Opera | 侧边栏服务聚合 | 轻量入口设计 | 捆绑推广伤信任 |
| Atlas | 内核服务化 + Agent | OWL/Mojo 解耦思路 | 双平台固定成本、注入风险 |
| 360/QQ/搜狗 | 双核兼容 + 快速升核 | 升核纪律、IE 兼容 | 老基线停版 |
| 龙芯/红莲花/360信创 | 国密 + 管理端 + 适配 | 三件套产品结构 | 资质周期低估 |

### 格局判断

2026 年的桌面浏览器竞争已从“能不能渲染网页”转向三件事：更新速度（Chrome 双周发布把 N-day 窗口压到极短 [2]）、AI/Agent 入口（大厂内建，中小厂商难以正面对抗）、以及垂直场景（政企管控、国密信创、内网专用）。对自研团队而言，最现实的生存位是“垂直场景的受控浏览器”：客户要的不是通用上网，而是可管控、可审计、可离线、过国密与等保的专用客户端——这类需求套壳满足不了，恰好是内核二次开发的价值区间。

### 决策标准：什么时候值得做

值得自建内核分支，当且仅当以下至少三条成立：一是需求必须触达内核层（国密 TLS、自定义网络栈与代理审计、进程模型与沙箱策略、深度 UI 重构），套壳无法实现；二是你有长期平台团队（≥10 人常驻）与 3 年以上预算承诺，能承受双周上游节奏下的月度跟版；三是目标客户为政企/信创/内网专用场景，愿意为管控与合规付费，且你能拿到商密与适配资质；四是存在渠道或预装/项目交付能力，否则发版再好也无人安装。

应改为 CEF/WebView2/Electron 套壳，当：需求止于“固定入口 + 少量原生能力 + 内网 Web 应用”，不需要自定义网络栈与国密，团队 <5 人，周期要求 <3 个月。应直接采购成熟下游（360/龙芯/红莲花等信创浏览器或商业 OEM 方案），当：核心诉求是资质与交付速度而非差异化，或你无法承诺永久 10 人平台团队——采购方通常已承担跟版与资质成本，你只做品牌与策略层定制即可。

一个实用的中间路线是“先套壳验证、再分支化”：用 WebView2/WKWebView 快速验证产品与付费意愿，同时并行做 Chromium POC；当付费客户明确要求国密、离线策略或深度管控时，再把已验证的 UI 与策略层迁移到分支。这样把 12～18 人的重投入推迟到需求被验证之后。

### 一线开发者的第一周行动清单

第 1 天：固定工具链镜像（depot_tools + VS/Xcode 版本 + build deps），一人一机编出原生 Chromium 并启动，记录耗时与磁盘。第 2 天：建 `upstream/M` 与 `downstream/M` 分支，跑通一次 `gclient sync --with_branch_heads` 与 `gn gen`，把命令写进仓库 `BUILDING.md`。第 3 天：完成品牌替换最小集（产品名、图标、关于页）并出 Windows 与 macOS 包。第 4 天：改默认搜索与首跑 pref，关掉非必要外发，产出补丁并用 `git format-patch` 归档为补丁集。第 5 天：做一次“假跟版”演练——切到相邻小版本分支重放补丁，统计冲突文件数，这个数字就是未来几年维护成本的真实预告。第 6～7 天：把签名、公证、更新器清单、崩溃上报四件事的流水线骨架搭起来（哪怕先内测自签），并产出合规清单初稿交法务。能在一周内走完这七步的团队，才具备开项目的资格；走不完，先补构建与发布能力，别先写功能。

## 十一、附录：速查、入口与术语

这一章是贴在工位上的速查页：命令、官方入口、术语释义。读完你可以不查文档完成日常构建与跟版动作。

### 常用命令速查

```bash
# 同步与分支
fetch --nohooks chromium            # 首次拉取
gclient sync --with_branch_heads --with_tags -j 8
gclient sync --disable-sync  0      # 仅同步指定依赖（排障用）
git checkout -b downstream/M refs/remotes/branch-heads/M

# 构建配置与编译
gn gen out/Debug --args='is_debug=true is_component_build=true symbol_level=2'
gn gen out/Release --args='is_debug=false is_component_build=false symbol_level=1 blink_symbol_level=0 use_jumbo_build=true'
gn args out/Release --list | grep -i sandbox
ninja -C out/Release chrome
ninja -C out/Release mini_installer      # Windows 安装包
autoninja -C out/Debug chrome            # 自动并行度，日常推荐

# 调试与诊断
out/Debug/chrome --no-first-run --user-data-dir=/tmp/p --enable-logging=stderr --v=1
out/Debug/chrome --remote-debugging-port=9222
out/Debug/browser_tests --gtest_filter=MyFeature*
git cl format && git cl presubmit

# 补丁与跟版
git format-patch upstream/M..downstream/M -o patches/
git am patches/*.patch                  # 在新基线上重放
git rebase upstream/M downstream/M

# 签名与公证（macOS）
codesign --deep --force --options runtime --timestamp --sign "Developer ID Application: X" My.app
xcrun notarytool submit My.dmg --keychain-profile "AC" --wait
xcrun stapler staple My.dmg
```
