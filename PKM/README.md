# PKM · 知识连接层

> **一句话**：本仓的笔记方式已从「文件夹即数据库」升级为
> **「文件夹（归档轴）＋ 索引（检索轴）＋ 连接层（知识轴）」三轴并行**。

## 是什么

`PKM/` 是 `write` 工作区的**知识连接层** —— 让 1169 个 Markdown 文件
从「能翻目录找到」升级为「能检索、能导航、能发现关联」。

**它不是什么**：不是新的笔记软件，不取代 Obsidian / 思源 / Logseq，
不搬走任何内容，不产生第二份真相源。

## 目录

| 路径 | 内容 | 入库 |
|---|---|---|
| `00-原子笔记/` | **原子笔记**（9 篇：8 篇永久笔记 + 1 篇指南） | ✅ 知识资产 |
| `01-MOC/` | **MOC 内容地图**：跨项目导航 ＋ 原子笔记索引 ＋ 16 份项目级 MOC | ✅ 知识资产 |
| `02-索引/` | 受控登记：文档元数据清单 ＋ 项目关联登记表 | ✅ 知识资产 |
| `MOC-全库.md` | 全库内容地图（脚本生成骨架 + 人工补充） | ✅ |
| `graph.json` | **知识图谱**（文档元数据 + 双向连接） | ✅ |
| `孤立文档清单.md` | 连接层施工单（按项目分组，知识/叙事分列） | ✅ |
| `断链清单.md` | 断链体检结果 | ✅ |
| `index.json` | **全文倒排索引**（派生缓存） | ❌ 不入库 |

> **为什么 index.json 不入库**：它是派生产物，`npm run pkm:build` 10 秒可重建，
> 入库只会制造 17MB 的 diff 噪音。纪律与「审校报告不入库」同源。
> **入库的是知识资产**（图谱 / MOC / 原子笔记）—— 那才是人工积累的价值。

## 原子笔记：跨项目复用的最小单元

**一块乐高只装一个想法。** 判定标准只有一条：
**「这条能独立搬到别的项目里用吗？」** 能，才是原子笔记；
不能，它还只是某本书的设定条目（那些留在各自的 `bible/` 里）。

收录三标准（详见 [[PKM/01-MOC/MOC-原子笔记索引.md]]）：
跨项目可移植 ＋ 一块乐高只装一个想法 ＋ 可追溯（指到 file + 章节）。

当前 8 篇永久笔记：

| 笔记 | 类型 | 一句话 |
|---|---|---|
| [[atom-0001 战锤四神体系]] | 共享设定 | 廓者 × 战锤42 同宇宙；去 GW 化必须同步 |
| [[atom-0002 通用模板包]] | 方法论资产 | 全仓唯一方法论真理源 ＋ 反哺闭环 |
| [[atom-0003 同题材共享语汇口径]] | 创作口径 | 同赛道靠自身特点立住；共享要记账不避让 |
| [[atom-0004 基准系统＋白名单]] | 设定技术 | 一句铁律＋微调白名单，替代穷举式设定 |
| [[atom-0005 六栏结算制]] | 流程机制 | 卷完按人物/支线/台账/实体/风格/方法强制回填 |
| [[atom-0006 考据与虚构三层分档]] | 标注口径 | 把「有没有典据」变成可判定的三档 |
| [[atom-0007 模板不适用是阶段属性]] | 认识论 | 过早的「不适用」判定是伪判定 |
| [[atom-0008 冻结与不回改前文]] | 生命周期 | 补漏任务表 ≠ 修订清单 |

> **元层观察**：8 篇里有 3 篇（0006 / 0007 / 0008）不是「怎么写」，
> 而是**「怎么判断」** —— 判定能否声称有典据、判定模板适用性、判定能否改稿。
> 这类元方法论比技法更可移植，因为它不依赖具体题材。

## 三层连接结构

```
第一层：项目级 MOC（自动生成 16 份）── 给簇内每个知识节点提供入链
   │   └─ 节点文件本身零改动（旁挂机制）
   ▼
第二层：跨项目 MOC（人工维护）── 跨作品导航 + 题材簇辨析
   │   └─ 链接全部项目级 MOC
   ▼
第三层：原子笔记（人工维护）── 跨项目复用的设定/口径/方法论
       └─ 链接到具体文档，是「真正的知识」所在
```

**实测效果**（2026-11-14）：

| 指标 | 建层前 | 建层后 |
|---|---|---|
| 出链总数 | 102 | **1333**（13 倍） |
| 知识节点孤立率 | 100% | **0.0%** |
| 叙事节点孤立 | 1127 | 0（按设计不建链） |
| 断链 | — | 0 |

> **关键设计**：不给 564 篇设定逐篇写双链（做不到，也会违反零改动铁律），
> 而是用 **LYT 枢纽节点法** —— 每个项目一份 MOC，由它给簇内所有节点提供入链。
> 一次生成，全部脱离孤立。

## 快速开始

```bash
npm run pkm:search 战锤四神                    # 全仓检索
npm run pkm:links 廓者未名夜/作品总览.md        # 查出链 / 入链
npm run pkm:build                              # 重建索引 + 图谱 + MOC
npm run pkm:graph                              # 图谱统计
npm run check                                  # 闸门（含连接层体检）
```

## 方法论依据

| 方法论 | 在本仓的落法 |
|---|---|
| **Zettelkasten**（卡片盒） | 原子笔记：一块乐高只装一个想法；原子化后可跨项目复用 |
| **PARA**（四层分类） | 归档轴已由目录结构天然承担（作品项目＝Project/Archive，素材＝Resource） |
| **LYT**（链接你的思考） | **三层 MOC**：项目级 MOC（枢纽，给簇内节点入链）→ 跨项目 MOC → 原子笔记 |
| **Backlink / 反向链接** | 索引器自动计算 `backlinks`，双向可导航 |

## 受控登记（人工维护 · 机器消费）

两张表是**连接层的人工输入**，由 build 自动消费：

| 表 | 登记什么 | 消费方式 |
|---|---|---|
| `02-索引/文档元数据清单.md` | 给**已有文档**补 tags / aliases / type | 合并进图谱（旁挂，不改源文件） |
| `02-索引/项目关联登记表.md` | **项目之间**真的共享了什么 | 自动补项目 MOC 的「相关项目」互链 |

> **为什么不硬编码在 MOC 里**：MOC 是**生成物**，手写内容会被覆盖；
> 关联关系是**会变的知识**（今天同宇宙，明天可能拆开），
> 必须有独立的、可 diff、可追溯的登记处。

## 叙事节点 vs 知识节点

初版统计报「孤立 96.3%」，那个数字**误导施工方向** —— 它把两类东西混在了一起：

| | 数量 | 是否该建知识链 |
|---|---|---|
| **知识节点**（设定/模板/总览） | 628 | ✅ 是 —— 连接层的服务对象 |
| **叙事节点**（正文） | 563 | ❌ 否 —— 线性叙事，靠卷/章顺序组织 |

正文逐章互链只会制造噪音。因此：**孤立率以知识节点为分母**，
叙事节点单列观察。这是本仓的口径修正。

## 与 Obsidian 的关系（可选外壳）

本仓是**纯 Markdown**，Obsidian 可以「Open folder as vault」直接指向仓根 ——
**零迁移**，立刻获得图形化双链与图谱视图。

但 Obsidian **不是必需品**：
- 本仓自带的检索器对中文做了二元组切分，比 Obsidian 原生搜索更准；
- Obsidian 核心闭源、Sync 付费，中文分词需另装 Omnisearch；
- 万级文件以上 Obsidian 索引会明显变慢。

所以本仓的定位是：**仓库即 vault**，Obsidian 只是「其中一种看法」。

## 纪律

1. **正文零改动**：不批量给已有 1169 个文件注入 frontmatter —— 连接关系放在
   原子笔记里（旁挂机制），文档本身不动。
2. **只读源文件**：索引器只读，只写 `PKM/`。
3. **零三方依赖**：Python 内核只用标准库，换机即跑。
4. **断链即错链**：同名歧义一律判为断链（宁可断，不可错）。
5. **闸门只看 ERROR**：断链＝ERROR（会让知识网络给出错误答案）；孤立比例＝WARN（施工单）；规模＝INFO。
