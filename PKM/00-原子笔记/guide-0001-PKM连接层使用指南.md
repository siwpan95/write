# PKM 连接层使用指南

> **一句话**：本仓的笔记方式已从「文件夹即数据库」升级为
> **「文件夹（归档轴）＋ 索引（检索轴）＋ 连接层（知识轴）」三轴并行**。

## 为什么不是「装个笔记软件」

全哥这个仓不是通用知识库，是**创作工作区**：12 部网文 + 素材 + 工具链。
通用 PKM 工具（Obsidian / 思源 / Logseq）都要求「先把内容搬进它的库」，
本仓不做这个动作 —— 一是 1161 个 md 一个字节不动（守《工作区规范》§五「正文零改动」），
二是避免第三份真相源与 git 仓库打架。

所以本仓走的是**「仓库即 vault」**路线：
Markdown 是唯一真相源，git 是版本与同步层，PKM 能力由仓内工具链提供。

## 三轴分工

| 轴 | 载体 | 回答什么问题 | 谁维护 |
|---|---|---|---|
| **归档轴** | 目录结构（已成熟，不动） | 「这文件属于哪个作品／哪一卷？」 | 现有规范（§一~§三） |
| **检索轴** | `PKM/index.json`（派生缓存） | 「全仓哪里提到过 X？」 | 自动重建，不入库 |
| **知识轴** | `PKM/graph.json` + 原子笔记 + MOC | 「这些设定之间是什么关系？」 | **人工积累，入库** |

## 日常怎么用

```bash
npm run pkm:search 战锤四神      # 全仓检索（中文二元组切分，零依赖）
npm run pkm:links 廓者未名夜/作品总览.md   # 看某文档的出链／入链
npm run pkm:build                # 重建索引 + 图谱 + MOC
npm run pkm:graph                # 图谱统计
```

## 新增知识怎么写

**先写原子笔记**（`PKM/00-原子笔记/`），再把已有文档**链过来**。

原子笔记的纪律（Zettelkasten 的「一块乐高只装一个想法」）：

1. **一条笔记只讲一件事**。跨项目复用的设定／口径／方法论，才值得独立成篇。
2. **写自己的话**，并注明**出处**（file + 章节）—— 可追溯才算知识资产。
3. **用 `[[双链]]` 指向相关笔记与文档**。这是连接层的全部意义。
4. **frontmatter 必填**：`id` / `title` / `type` / `status` / `created` / `projects` / `tags`。

### 原子笔记的收录标准（决定要不要立一条）

**一条内容要不要立为原子笔记，看三条，全中才收：**

| # | 标准 | 反例（不该收录） |
|---|---|---|
| 1 | **跨项目可移植** —— 换个项目还成立 | 「赵海是本书主角」→ 留在本书 bible |
| 2 | **一块乐高只装一个想法** —— 一句话能说清 | 「本书的创作方法论」→ 太笼散，拆 |
| 3 | **可追溯** —— 能指到原文出处 | 凭印象总结 |

**宁缺毋滥** —— 原子笔记的价值在于每条都能复用；一旦掺进只对本项目有用的内容，
整份笔记的迁移性就毁了。

> 判定捷径：**「这条能独立搬到别的项目里用吗？」**
> 不能 → 它还只是某本书的设定条目，留在那本书的 `bible/` 里就够。

### frontmatter 字段规范

| 字段 | 取值 | 说明 |
|---|---|---|
| `id` | `atom-NNNN` | 永久唯一，**创建后不改**（改了就断链） |
| `title` | 文本 | 与文件名一致，便于双链解析 |
| `type` | `永久笔记` / `文献笔记` / `临时笔记` / `指南` | Zettelkasten 三型 + 指南 |
| `status` | `稳定` / `草稿` / `待复核` | 未落定的别标「稳定」 |
| `created` | `YYYY-MM-DD` | |
| `projects` | 列表 | 涉及哪些作品（空列表＝跨项目） |
| `tags` | 列表 | 受控词表，见下 |

### 受控标签词表

标签是**检索入口**，必须收敛，否则会退化成噪音（当前全仓历史标签 137 处、有效仅 6 个文件）。

| 前缀 | 含义 | 例 |
|---|---|---|
| `设定/` | 设定类 | `设定/共享宇宙`、`设定/人物` |
| `口径/` | 判断规则 | `口径/创作`、`口径/合规` |
| `方法论/` | 做事方法 | `方法论/模板`、`方法论/题材` |
| `体系/` | 设定体系 | `体系/四神`、`体系/境界` |
| `IP/` | 版权与合规 | `IP/战锤40K` |
| `资产/` | 资产类型 | `资产/跨项目` |
| `指南/` | 使用说明 | `指南/PKM` |

## 已有文档怎么接进来（不改正文）

**不批量注入 frontmatter** —— 1161 个文件批量改会污染 diff、违反零改动铁律、
且让「正文改动」与「笔记改动」混在一起无法审计。

采用**旁挂（sidecar）** 机制，三条路径：

1. **项目级 MOC（自动）** —— `npm run pkm:build` 为每个项目生成一份 MOC，
   由它给该项目内的全部知识节点提供入链。**节点文件一个字节不动**。
   这已覆盖绝大多数连接需求（实测：知识节点孤立率 100% → 0.0%）。
2. **原子笔记（人工）** —— 跨项目复用的设定/口径/方法论，写成独立笔记并双链过去。
3. **受控清单（人工）** —— `PKM/02-索引/文档元数据清单.md`（补 tags/aliases）、
   `PKM/02-索引/项目关联登记表.md`（项目间共享），由索引器合并进图谱。

需要给单个文档补元数据时，用受控清单，**依然不碰正文**。

## 孤立率的口径（重要）

**孤立率以「知识节点」为分母**，不是全部文档。

| | 数量 | 是否该建知识链 |
|---|---|---|
| 知识节点（设定/模板/总览/台账） | 628 | ✅ 是 |
| 叙事节点（正文） | 563 | ❌ 否 —— 线性叙事，靠卷/章顺序组织 |

初版统计把两者混算，报出「96.3% 孤立」—— 数字虚高且**误导施工方向**
（会让人去给 563 篇正文逐章互链，那是噪音不是知识）。
正文只在项目 MOC 里列**章节目录**（普通相对链接，可点击导航），不建知识双链。

## 增量的正确姿势

新建笔记 → 写好 frontmatter + 双链 → `npm run pkm:build` → 看 `PKM/孤立文档清单.md`
里你的新笔记是否已脱离孤立 → 提交。

**孤立文档清单是施工单，不是耻辱榜**：它告诉你「还有哪些内容没接入知识网络」，
按项目分批补，一次补一个项目的一个角色层（例如先把《廓者》的 12 份 SSOT 链起来）。

## 换机怎么办

见 `tools/bootstrap.sh`（一键）或 `PKM/换机部署.md`（手把手）。
核心只有一句：**git clone ＋ npm install ＋ npm run pkm:build**，
其余（索引、MOC、图谱）全部自动重建；Obsidian 只是可选的图形外壳，不是必需品。
