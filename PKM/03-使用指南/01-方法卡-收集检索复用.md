# 知识库使用方法（收集 → 检索 → 复用）

> **一句话**：本仓的知识库**不是用来存的，是用来取和用的**。
> 存进去靠纪律，取出来靠检索，用出去靠复用 —— 三步各有一个明确动作和一件明确产出。

> **给谁看**：想「用」这个知识库的人（不是想建它的人）。
> 已有体系说明见 [[PKM/00-原子笔记/guide-0001-PKM连接层使用指南.md]]；
> 本文只讲**动作**，不重复原理。

---

## 方法卡（速查版）

| 步骤 | 一句话 | 输入 | 输出 | 判定完成 |
|---|---|---|---|---|
| **① 收集** | 把一个**可复用的判断**写成一条原子笔记 | 一个想法／一处踩坑／一条设定 | `atom-NNNN-*.md` 一条笔记 | 过得了「三标准」（见下） |
| **② 检索** | 用**关键词**换**专名**，把结果当线索不当答案 | 一个模糊问题 | 一条**可执行的出处**（file + 章节） | 找到了「指哪打哪」的那一行 |
| **③ 复用** | 把这条笔记**用进正在写的稿子**，并记账 | 一条笔记 + 一个施工点 | 稿子里的一处改动 + 一条记账 | 稿子真的变了，且知道来源 |

> **三步是环**：复用时发现新问题 → 回到 ① 收集 → 再走 ② ③。
> **不做 ① 就没法做 ②③**（没有可检索的原子笔记，检索器只能命中原文）。
> **不做 ② 就没法做 ③**（找不到出处的知识不敢用 —— 用错了比不用更贵）。

---

## 第一步 · 收集

### 做什么

**只收「可复用的判断」，不收「资料」。** 这是本方法与「随手记」的唯一区别。

一句话判定：**「这条能独立搬到别的项目里用吗？」**

- 能 → 值得写成一条原子笔记（进知识轴）
- 不能 → 它是某本书的设定条目，**留在那本书的 `bible/` 里就够了**（这是正确处置，不是失职）

> 把项目专属设定硬塞进知识轴，会毁掉整份笔记的迁移性 —— 笔记一旦掺进
> 只对本项目有用的内容，就再也搬不动了。这是 [[atom-0007 模板不适用是阶段属性，不是项目属性]]
> 的同一条道理：**过早的「不该收录」是伪判定，但过早的「全部收录」同样是伪判定。**

### 三条收录标准（全中才收，宁缺毋滥）

| # | 标准 | 反例（不该收） |
|---|---|---|
| 1 | **跨项目可移植** —— 换个项目还成立 | 「赵海是本书主角」→ 留在本书 `bible/` |
| 2 | **一块乐高只装一个想法** —— 一句话说得清 | 「本书的创作方法论」→ 太笼统，拆开 |
| 3 | **可追溯** —— 能指到原文出处 | 凭印象总结 → 要么补出处，要么别收 |

### 输入 → 动作 → 输出

| 项 | 内容 |
|---|---|
| **输入** | 写作过程中冒出的一个**判断**（不是一段资料）。典型三类：① 踩过的坑 ② 想通的口径 ③ 可移植的设定 |
| **动作** | ① 用上面三条标准筛 ② 写成一条 `atom-NNNN-*.md` ③ frontmatter 七字段必填 ④ 用 `[[双链]]` 指向相关笔记与文档 ⑤ 末尾写「出处」段 |
| **输出** | 一条 `PKM/00-原子笔记/atom-NNNN-标题.md`，字段齐全、双链到位、出处可查 |

### 写完立刻做（增量维护的正确姿势）

```bash
npm run pkm:build     # 重建索引 + 图谱 + MOC
npm run pkm:doctor   # 环境与产物自检
npm run check         # 闸门：ERROR 0 = 可放行
```

然后看 `PKM/孤立文档清单.md` —— **新笔记是否已脱离孤立**。
（这张清单是**施工单**，不是耻辱榜：它只告诉你「还有什么没接入知识网络」。）

### 铁律

1. **不批量给已有文件注入 frontmatter** —— 违反《工作区规范》§五「正文零改动」，
   且会让正文改动与笔记改动混在一起无法审计。需要给已有文档补 tags/aliases 时，
   走 `PKM/02-索引/文档元数据清单.md` 旁挂。
2. **`id` 创建后不改** —— 改了会断链。
3. **标签走受控词表**（见下方模板）—— 标签是检索入口，不收敛就退化成噪音。

## 第二步 · 检索

### 做什么

**用「关键词」换「专名」。** 这一步的全部难点在此。

本仓检索器（`tools/pkm/indexer.py`）的实测行为（2026-11-19 验证）：

| 机制 | 实测结论 | 对用法的含义 |
|---|---|---|
| **二元组切分** | 中文按 2 字切连续汉字串，无词典 | 搜**专名**（连续词）命中准；搜**口语长句**会散 |
| **IDF 加权** | 罕见词权重高（`战锤四神` → 66.6 分） | 专有名词的区分度最高 |
| **标题 ×3 / 正文 ×1 / 标题+正文 ×1.5** | 标题命中权重极高 | **文件名里带关键词的文档会被顶上来** |
| **覆盖率折扣** | `score ×= (0.4 + 0.6 × 覆盖率)` | 只命中一个词的文档被压到后面 —— 有效抑制噪声 |
| **几乎不返空集** | 搜「绝不存在qqqq」仍返回 3 条（8.0 分） | **搜不到 ≠ 不存在**，见下方常见问题 |

### 输入 → 动作 → 输出

| 项 | 内容 |
|---|---|
| **输入** | 一个**模糊问题**（「怎么让主角更有魅力」）或一个**专名**（「爽感」「战锤四神」） |
| **动作** | ① 先搜专名，看 Top3 ② 不对就换**同义专名**（不是加长句子）③ 用 `--project` / `--type` 收窄 ④ 还不确定就看**入链/出链**找邻居 |
| **输出** | 一条**能指到具体位置**的出处（`文件路径` + 章节），而不是「好像在某个设定里」 |

### 四条命令（全部实测可跑）

```bash
# 1) 基础检索：中文二元组切分，零依赖
npm run pkm:search 爽感

# 2) 收窄范围：只在某项目 / 某类型里找
npm run pkm:search 爽感 --project 综网废柴逆命 --limit 5
npm run pkm:search 战锤 --type PKM --limit 5

# 3) 查邻居：找出链 / 入链（这是「找不到」的第一手备用路）
npm run pkm:links "PKM/00-原子笔记/atom-0005-六栏结算制.md"

# 4) 全景与自检
npm run pkm:graph    # 图谱统计（文档数 / 连接数 / 断链）
npm run pkm:doctor   # 环境自检
```

### 检索的四条降级路径（按顺序试）

| 顺序 | 动作 | 适用场景 |
|---|---|---|
| 1 | **搜专名** | 已知要什么 |
| 2 | **换同义词再搜** | 搜不到 —— 换个说法（不是加长句子） |
| 3 | **加 `--project` / `--type` 收窄** | 结果太杂 |
| 4 | **走出链/入链** | 完全不知道在哪 —— 从你已知的那篇往邻居走 |

> **第 4 条最被低估**。人记不住「那篇笔记叫什么」，但**记得住「跟谁一起出现过」**。
> `pkm:links` 就是把这种记忆变成可执行路径。

## 第三步 · 复用

### 做什么

**把笔记用进正在写的稿子，并留痕。** 这是知识库产生复利的唯一环节 ——
只收不用，知识库就是一座越来越贵的仓库。

### 输入 → 动作 → 输出

| 项 | 内容 |
|---|---|
| **输入** | 一条原子笔记 + 一个**具体施工点**（「第二卷第 3 章要安排主角的第一次代价」） |
| **动作** | ① 打开笔记，看它的「适用边界」 ② 确认这条真能用在**这个**施工点上 ③ **按笔记改稿** ④ 在笔记的「出处」或项目台账里**记一笔**：哪个文件、哪一章、怎么用的 |
| **输出** | 稿子里的一处**具体改动**（不是「参考了某笔记」这种空话）＋ 一条**可追溯的复用记录** |

### 为什么必须记这一笔

**没有复用记录的原子笔记，等于没被复用过的电子表格。**

记下来之后，这三件事自动成立：

1. **下次同类问题能秒查** —— 「上次这个坑怎么解的」有了答案；
2. **笔记的适用范围被验证或推翻** —— 用不了就该改 `status`，而不是让它继续装作「稳定」；
3. **高价值笔记自然浮出** —— 被用过 5 次的笔记，和从没被用过的笔记，在 `status` 上就该不一样。

### 复用时最容易犯的两个错

| 错 | 后果 | 正确做法 |
|---|---|---|
| **「参考了某笔记」但没落到具体位置** | 账记了，人没受益，下次还是找不到 | 必须写到 **file + 章节** 级 |
| **笔记说「稳定」但实际用不了** | 后续复用踩坑，信任被透支 | 用不了就改 `status: 待复核`，并写明卡在哪 |

## 与现有体系的关系（不重复造轮子）

| 层 | 载体 | 本方法在哪一步用 |
|---|---|---|
| **归档轴** | 目录结构（已成熟，不动） | ① 的「留在 `bible/`」判定 |
| **检索轴** | `PKM/index.json`（派生缓存） | ② 全部 |
| **知识轴** | 原子笔记 + MOC + `graph.json` | ① 的产出、③ 的对象 |

**本方法不新增任何目录结构、不改动任何既有文件。**
它只规定「人在什么时候做什么动作」。
