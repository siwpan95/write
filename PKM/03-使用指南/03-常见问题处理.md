# 常见问题处理

> 两个高频问题，按**真实发生的顺序**排：
> 一、找不到旧笔记；二、笔记太多不整理。
>
> 全部结论基于 2026-11-19 对本仓工具链的**实测**（不是通用建议）。

---

# 问题一：找不到旧笔记

## 先搞清楚：你的情况是哪一种

**实测发现（关键）**：本仓检索器**几乎不返回空集**。

| 你搜的 | 实际返回 |
|---|---|
| `战锤四神` | 42 行，Top1 得分 66.6（精确命中） |
| `爽感` | 42 行，Top1 = `26_爽感与节奏设计.md`（21.99 分，精确） |
| `绝不存在qqqq` | **仍有 3 条结果（8.02 分）** |
| `qqqqzzzxyw`（纯 ASCII 乱词） | 真空集 |

**含义**：
- **搜出一堆不相关的东西 ≠ 搜不到**，而是**查询词选错了**；
- 纯中文查询几乎总是有结果（二元组总能撞上一些常用词）。

## 排查顺序（按这个走，不要跳步）

### 第 1 步：确认「记错了名字」不是「记错了概念」

人记不住的是**文件名**，记得住的是**概念**。
搜文件名大概率失败 —— 搜**概念里的专名**。

```bash
npm run pkm:search 爽感              # ✅ 专名 → 精确命中
npm run pkm:search 26_爽感与节奏设计   # ❌ 文件名片段 → 未必命中（标题里没这些字）
```

> 文档**标题**与**文件名**不一定一致。检索器对**标题**加权 ×3、对**正文** ×1 ——
> 所以搜「内容里会出现的词」比搜「文件名」有效。

### 第 2 步：换同义专名再搜（**不是**把句子写长）

实测对比：

| 查询 | Top1 | 说明 |
|---|---|---|
| `爽感` | `26_爽感与节奏设计.md`（21.99） | 专名，精确 |
| `怎么让主角更有魅力` | `13-世界先行与地图叙事模板.md`（15.44） | 长句被二元组切碎，**散** |

**原因**（`tools/pkm/indexer.py`）：
中文按**二元组（2 字）**切分，**无词典**。长句被切成几十个碎片，
每个碎片权重低；而覆盖率折扣 `score ×= (0.4 + 0.6 × 覆盖率)` 会压低只命中少数词的文档。

**动作**：把长句换成**2～4 字的专名**重试。

- ✗ `怎么让主角更有魅力` → ✓ `人物弧光` / `角色动机` / `欲扬先抑`

### 第 3 步：加过滤器收窄范围

```bash
npm run pkm:search 爽感 --project 综网废柴逆命 --limit 5
npm run pkm:search 战锤 --type PKM --limit 5
```

实测：`--project 综网废柴逆命` 把 Top1 分数从 21.99 提到 **109.94**
（因为筛掉了其他项目的干扰文档）。

### 第 4 步：走出链/入链（**最被低估的一招**）

完全不知道在哪时，别再猜关键词了 —— **从你已知的那篇往邻居走**。

```bash
npm run pkm:links "PKM/00-原子笔记/atom-0005-六栏结算制.md"
```

实测输出：出链 7 条、入链 15 条。
**入链**告诉你「哪些笔记和它一起出现过」—— 人记不住文件名，
但**记得住跟谁一起出现过**。这正是 `pkm:links` 的价值。

> 手动查双链也可以：打开 `PKM/01-MOC/MOC-原子笔记索引.md` 看主题分类，
> 或打开 `PKM/MOC-全库.md` 看全库地图。

### 第 5 步：确认它是不是「在归档里」

旧稿、废弃稿**同样被索引**（实测 `include_archived=True`）：

```bash
npm run pkm:search 六维全一
# → Top1: 综网废柴逆命/_archive/废弃旧稿/第01章_六维全一.md （63.14 分）
```

**所以「找不到旧笔记」常常是「它归档了，但索引找得到」**。

### 第 6 步：还是不行 —— 走人查

```bash
git log --oneline --all --grep="关键词"     # 提交信息
git grep -n "关键词" -- "*.md"              # 全库原文精确匹配（绕开二元组）
```

`git grep` 是**逐字匹配**，绕开二元组切分 —— 是检索器的兜底，不是替代品。

### 速查表

| 症状 | 先试这个 |
|---|---|
| 搜出一堆不相关 | 换 2～4 字**专名**，别加长句子 |
| 结果太杂 | `--project` / `--type` 收窄 |
| 完全想不起在哪 | `pkm:links` 从已知文档走向邻居 |
| 只记得旧稿 | 直接搜，**归档目录已被索引** |
| 什么都搜不到 | `git grep` 逐字兜底 |

# 问题二：笔记太多不整理

## 先纠正一个前提：**「不整理」通常不是问题，「乱整理」才是**

实测数据（本仓现状）：

| 指标 | 值 |
|---|---|
| 索引文档数 | **1,608** |
| 出链总数 | 2,538 |
| **断链** | **0** |
| 知识节点孤立率 | **0.1%**（1 篇：`CHANGELOG.md`） |
| 叙事节点（正文）孤立 | **0**（设计如此 —— 正文不该有知识链） |

**这意味着知识网络本身是健康的。** 1581 篇知识节点中只有 1 篇孤立。
「笔记太多」是**数量现象**，不是**结构故障**。

**因此第一原则：不要为了减少数量而整理。** 整理会引入断链、破坏引用、
把「按需生长」变成「按目录生长」。

## 正确的应对：三条，按成本从低到高

### 应对 1：不整理，改用**收窄检索**（零成本，覆盖 80% 的场景）

「太乱」的真实诉求是**找不到**，不是**数量多**。
那就用过滤器，不动文件：

```bash
npm run pkm:search 爽感 --project 综网废柴逆命 --limit 5   # 按项目
npm run pkm:search 战锤 --type PKM --limit 5               # 按类型
```

**目录不整理，检索来收窄。** 这是本仓架构的核心主张。

### 应对 2：新内容**只进一个口子**（防扩散）

从源头控制量：

| 内容类型 | 去哪 | 不要去哪 |
|---|---|---|
| 只对本项目有用 | 该项目 `bible/` / `设定/` | ❌ 不要立原子笔记 |
| 跨项目可复用的判断 | `PKM/00-原子笔记/atom-NNNN-*.md` | ✅ 唯一收口处 |
| 已有文档要补 tags | `PKM/02-索引/文档元数据清单.md` | ❌ 不要改正文 |

> **这一条最关键**：项目专属的东西留在项目里，**不进入知识轴**。
> 知识轴只装「换个项目还成立」的东西 —— 总量自然可控。
> （这正是 [[atom-0007 模板不适用是阶段属性，不是项目属性]] 的应用。）

### 应对 3：真要清理，只清**三种**，且有硬前置

**三种可清**：

| 类型 | 判据 | 动作 |
|---|---|---|
| **草稿态原子笔记** | `status: 草稿` 且从未被复用 | 合并进成熟笔记，或标 `status: 待复核` |
| **重复笔记** | 两条讲同一件事 | 留一条，另一条改成**指向**它的链接 |
| **失效笔记** | 标了 `待复核` 且确认已过时 | 登记进 `PKM/02-索引/失效条目登记表.md`，**不直接删** |

**四个硬前置**（缺一条就不许动）：

1. **冗余三查** —— 列功能面 → 逐面找实证接任者 → 无接任者不可删；
2. **先合并，后删除** —— 先把内容并进留存笔记，确认断链为 0，再删；
3. **登记进失效登记表** —— 删除也要留痕，不是删了就完了；
4. **git 可回取** —— 提交历史里随时能拿回来（这也是「可逆」的前提）。

### 明确**不要**做的三件事

| ❌ 不要 | 为什么 |
|---|---|
| **批量给已有文件注入 frontmatter** | 违反《工作区规范》§五「正文零改动」，且正文改动与笔记改动混在一起无法审计 |
| **按主题新建顶层目录** | 破坏归档轴的成熟结构 —— 目录结构是既成事实，不重新分类 |
| **为了「看起来整齐」而移动/重命名** | 会断链；且《工作区规范》§二明确「**不回溯改名历史归档**」 |

> ⚠️ **本方法卡本身就遵守这一条**：三份交付物全部是**新增文件**，
> 没有移动、没有重命名、没有改动任何既有文件的正文。

## 一句话结论

> **不整理，用检索收窄；新内容只进一个口子；真清理只清草稿/重复/失效三种，
> 且必须先合并、后登记、可回取。**

# 附：其他三个高频小问题

### Q：搜出来的笔记看着像，但套进我的稿子不合适

**先看它的「适用边界」**（模板里必须有这一节）。没有这节的笔记是**不合格笔记** ——
把它补上，或把 `status` 改成 `待复核`。
**别硬套** —— 硬套一条不匹配的笔记，比不套更贵。

### Q：笔记之间重复了怎么办

**不要新建第三条**。改法：留**最成熟**的那条（`status: 稳定` + 有复用记录），
其余改成指向它的链接 —— 这样既减少数量，又不丢内容，还保留了可追溯性。

### Q：我的笔记没被搜到

三查：① 跑过 `npm run pkm:build` 吗（索引是派生缓存，不 build 不入库）②
文件名/标题里有那个词吗（标题 ×3）③ 标签拼对了吗（受控词表，不是自由发挥）。
