## TL;DR

**诊断结论**：本仓**不是**传统 PKM 库，而是**创作工作区**；它已经有很强的**归档轴**（目录 + SSOT + 台账 + MOC 雏形），

**「Zettelkasten 连接层 + 自建中文检索 + 机械门禁」**，

> ⚠️ **重要修正（2026-11-14）**：上面的「96.3% 孤立」是**混算口径**，会误导施工方向。
> 它把两类完全不同的东西算在了一起：
> - **知识节点**（设定/模板/总览）—— 孤立是**真缺口**，是施工单

> 混算不仅数字虚高，更会让人去给正文逐章互链 —— 那是噪音不是知识。

## 二、联网调研与选型

### 2.1 方法论选型

调研了 Zettelkasten / PARA / LYT 三套主流方法论，逐条对照本仓实际：

| 方法论 | 核心 | 在本仓的适配度 | 采纳结论 |
|---|---|---|---|
| **Zettelkasten** | 原子笔记（一条一个想法）＋永久链接＋自下而上涌现 | **高** —— 本仓已有大量「设定条目」正是一块块乐高，只是缺 ID 与链接 | ✅ **采纳**，落为 `PKM/00-原子笔记/` |
| **PARA** | Project/Area/Resource/Archive 四层 | **中** —— 归档轴已由目录结构天然承担（作品项目＝Project，素材＝Resource，`_archive/`＝Archive） | ⚠️ **不新建 PARA 目录**（会与现有结构打架），改由现有结构承担 |
| **LYT** | MOC 内容地图 ＋ Home Note ＋ 流体框架 | **高** —— 单项目 MOC 已有，缺的正是**跨项目 MOC** | ✅ **采纳**，落为 `PKM/01-MOC/` |

> **重要取舍**：Zettelkasten 官方有专门讲小说的系列（*The Zettelkasten Method for Fiction*），
> 核心是「原子化人物卡／地点卡 ＋ 结构笔记（structure note）＋ 双向记账」。
> 本仓的 `bible/` 已经是这个形态的**内容层**，缺的正是**结构笔记与链接层**。

### 2.2 工具选型

调研了 Obsidian / 思源 SiYuan / Logseq / Joplin / Trilium 的 2026 现状：

| 工具 | 存储格式 | 对本仓的适配 | 判定 |
|---|---|---|---|
| **Obsidian** | 纯 Markdown | 可「Open folder as vault」零迁移；但核心闭源、Sync 付费（$4/月）、原生中文搜索弱（需 Omnisearch）、万级文件索引变慢 | ⚠️ **可选外壳**，非主存储 |
| **思源 SiYuan** | JSON + Markdown 混合 | **破坏 git diff 可读性**；导出需额外步骤；数据在 JSON 里 → 与「纯 Markdown 单一真相源」冲突 | ❌ 否决 |
| **Logseq** | Markdown/Org，大纲式 | 大纲结构**与长篇散文正文直接冲突** | ❌ 否决 |
| **Joplin** | 纯 Markdown | 树形够用，但图谱/双链弱，无脚本生态 | ❌ 否决 |
| **Trilium** | 自定义 JSON | 需自建服务器；非纯 Markdown | ❌ 否决 |

**核心判断**：本仓**已经是**一个 git 管理的纯 Markdown 库，且有 1161 个文件、660 万字、
不可回改的冻结卷。任何要求「先搬进它的库」的工具，都是**净损失**。

调研到的关键外部观点，与本仓判断一致：

> 「你的 wiki 就是 git 仓库里的纯 Markdown。Obsidian 是**读**的地方：
> 浏览页面、跟随链接、看图谱。它只读文件夹，从不与 GitHub 通信。
> **仓库才是系统**，Obsidian 只是其中一种看法。」
> —— *wareagledusty/wiki-federation-starter-kit*

> 「如果你以后试 Obsidian，只要看『Open folder as vault』、wikilink 与 backlinks、graph view
> —— 足够认出这个产品。**它不是云套件，不是笔记本运行时，也不是这套工作流的必需基础设施。**」
> —— *omid.dev, Obsidian on a Git Research Vault*

### 2.3 中文检索：为什么自建

Obsidian 原生搜索对中文支持一般（社区共识：需另装 Omnisearch 做中文分词）。
本仓 660 万字中文 + 1161 个文件，是中文检索的典型重载场景。

自建二元组（bigram）索引的理由：
- **零三方依赖**（与本仓 49 个 `.py` 同源纪律）→ 换机即跑，无需 `pip install`
- **中文子串召回好**：无需词典，对专有名词友好
- **可复跑、可校验**：索引可重建、结果确定，能进闸门
- **可做机械门禁**：断链、孤立度都能自动判定

**实测**：`npm run pkm:search 战锤四神` 命中 20 条，跨《廓者》《战锤42》《二十一世纪奇门遁甲》；
`search 真气` 命中《无敌不是他人路》核心设定 —— 与 README 记载一致。

## 三、落地方案

### 3.1 架构：三轴并行

```
归档轴（已有，不动）        检索轴（自动，派生）        知识轴（人工，入库）
─────────────────────    ─────────────────────    ─────────────────────
目录结构                 PKM/index.json            PKM/00-原子笔记/
每书的 SSOT + 台账       中文二元组倒排索引         PKM/01-MOC/
作品总览（MOC 雏形）      全库 10 秒可重建          PKM/graph.json（连接图谱）
                                              ↑ 不入库（派生产物）
```

**为什么是这个分工**：与本仓既有纪律同源 ——「审校报告」是派生产物不入库，
「通用模板包」是知识资产必须入库。索引是前者，图谱与原子笔记是后者。

### 3.2 组件清单

| 组件 | 路径 | 语言 | 依赖 | 职责 |
|---|---|---|---|---|
| 扫描器 | `tools/pkm/scanner.py` | Python | 标准库 | 扫描、分类、抽取元数据、解析双链 |
| 索引器 | `tools/pkm/indexer.py` | Python | 标准库 | 二元组分词、倒排索引、检索打分 |
| 图谱/MOC | `tools/pkm/graph.py` | Python | 标准库 | 生成图谱、MOC、孤立清单、断链清单 |
| CLI | `tools/pkm/pkm_cli.py` | Python | 标准库 | `build` / `search` / `links` / `graph` / `doctor` |
| Cordis 插件 | `tools/plugins/13-pkm.mjs` | Node | cordis | 提供 `ctx.pkm` 服务 |
| 检查器 | `tools/plugins/14-checker-pkm.mjs` + `tools/checkers/pkm_check.py` | Node + Python | 标准库 | 连接层体检，进闸门 |
| 部署脚本 | `tools/bootstrap.sh` / `tools/bootstrap.ps1` | Bash / PowerShell | — | 换机一键部署 |

### 3.3 关键设计决策（含踩坑记录）

| 决策 | 理由 |
|---|---|
| **不批量注入 frontmatter** | 1161 个文件批量改会污染 diff、违反《工作区规范》§五「正文零改动」、且让「正文改动」与「笔记改动」混在一起无法审计。改用**旁挂（sidecar）**：连接关系存在原子笔记里 |
| **同名歧义判为断链** | 多项目都有 `03-世界观圣经.md`。任选其一＝静默指错。**宁可断链，不可错链** |
| **代码块内的 `[[..]]` 不建链** | 讲解双链写法的笔记自身会产生假断链（Obsidian 同此行为） |
| **非 Markdown 目标不算断链** | README 指向 `index.html`／目录的链接是**有效**的，只是超出 Markdown 索引范围。判定口径统一到索引器与检查器两处 |
| **索引不入库** | 17MB 派生产物，10 秒可重建；入库只制造 diff 噪音 |
| **图谱入库** | 连接关系是人工积累的价值，必须跨机复用 |
| **索引器扫「已跟踪 ∪ 工作区」** | 只扫 `git ls-files` 的话，新建笔记必须先 `git add` 才能被检索 —— 与使用直觉相反 |

**实施中修掉的 3 个真 bug**（都有可复现证据）：

1. **检索漏召回**：评分里 `if score == 0: continue` 发生在 `score += body_hit` **之前** ——
   导致「只在正文命中、标题未命中」的文档被整批丢弃。实测 `search 真气` 返回 0 条，
   而倒排表里明明有 11 篇命中。修正后正常。
2. **多义链接错指**：同名文件被 `setdefault` 静默指向首个匹配。改为歧义即断链。
3. **CLI 参数污染**：`--limit 3` 的 `3` 被当成查询词（查询变成「战锤四神 3」）。
   改为成对跳过「选项及其取值」。

### 3.4 闸门口径

`npm run check` 现在含 4 个检查器，新增 `pkm`：

| 档 | 条件 | 语义 |
|---|---|---|
| **ERROR** | 断链（目标在仓内不存在） | 会让知识网络给出错误答案，必须阻断 |
| **WARN** | 孤立文档 > 50% | 需人工定性 —— 是施工单，不是错误 |
| **INFO** | 规模统计 | 观察项 |

> 当前：**ERROR 0 ／ 断链 0**。既有 136 条 WARN 是仓内存量，本次**未新增**。

## 四、换机快速部署

### 4.1 需求与解法

要求是「换机快速部署」。实测发现**当前状态直接 clone 会失败**：

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'cordis' imported from
D:\projects\repos\write\tools\host.mjs
```

`node_modules/` 不入库（正常），但没有任何脚本告诉新机器该怎么装 —— 这是既有缺口。

### 4.2 部署脚本

```bash
git clone https://gitee.com/siwpan/write.git
cd write
bash tools/bootstrap.sh            # Git Bash
# 或
powershell -ExecutionPolicy Bypass -File tools\bootstrap.ps1   # Windows
```

四步：**环境自检 → 装 Node 依赖 → 重建 PKM 索引 → 跑闸门**。

| 设计点 | 实现 |
|---|---|
| **幂等** | 已装则跳过；重复跑安全 |
| **零硬编码路径** | 一切相对仓根；Python 按「显式配置 → 环境变量 → PATH → 常见安装位置」探测 |
| **失败可见** | 任一步失败即中止并报原因，不静默跳过 |
| **零三方依赖** | PKM 内核只用标准库 → **不需要 `pip install`**，消灭换机常见故障源 |
| **可复现** | `package-lock.json` 锁 Node 依赖版本 |
| **Windows 原生** | `.ps1` 版独立可用（不强制依赖 Git Bash） |

**双端实测**：bash 与 PowerShell 两版均完整跑通（4/4 步、闸门 ERROR 0）。

部署脚本还顺手修了两个环境探测缺陷：PowerShell 下 `git` 在
`%LOCALAPPDATA%\Programs\<App>\resources\vendor\PortableGit` 下时找不到 —— 已加探测规则。

### 4.3 跨机一致性

| 内容 | 同步 | 一致性 |
|---|---|---|
| 正文 / 设定 / 素材 | git 双端 | 提交历史 |
| PKM 知识资产 | git 双端 | 提交历史 |
| 索引缓存 | 本地重建 | 可复现（同一输入同一结果） |
| Node 依赖 | `npm install` | lock 文件锁版本 |

## 五、给全哥的使用建议

### 立刻可做（小步）

1. **检索代替翻目录** —— `npm run pkm:search <关键词>`。
   「这个设定我以前在哪写过」从此是一次命令。
2. **从施工单补连接** —— 打开 `PKM/孤立文档清单.md`，按项目分批补。
   建议顺序：先补**跨项目关联**（《廓者》×《战锤42》），再补**单项目内的核心设定链**。
3. **写新设定时顺手建原子笔记** —— 只要是**跨项目复用**的（设定、口径、方法论），
   在 `PKM/00-原子笔记/` 独立成篇并链过去。

### 中期演进

4. **Obsidian 作为可选外壳** —— 装好后「Open folder as vault」指向仓根，
   零迁移获得图形化双链与图谱。务必把 `node_modules` 加进 Excluded files。
5. **MOC 随内容演化** —— `PKM/01-MOC/` 的 MOC 是「活的导航页」，
   新增原子笔记后往对应 MOC 加一行。

### 不建议做

- ❌ **不要**批量给已有 1161 个文件注入 frontmatter —— 违反零改动铁律，
  且污染 diff。要补元数据用 `PKM/02-索引/` 的受控清单旁挂。
- ❌ **不要**把 `PKM/index.json` 提交进库 —— 17MB 派生产物，10 秒可重建。
- ❌ **不要**为了「像 Obsidian」而重排现有目录 —— 归档轴已经健康，重排收益为负、风险极高。

## 六、结论

| 问题 | 答案 |
|---|---|
| 现在的笔记方式是什么？ | **强归档、弱检索、零知识轴**。目录与 SSOT 成熟，但 96.3% 文档孤立，无双链、无元数据、跨项目无连接 |
| 最适合的 PKM 路径？ | **仓库即 vault** —— Zettelkasten 连接层 ＋ 自建中文检索 ＋ 机械门禁，融入既有 Cordis 工具链 |
| 要装什么软件？ | **什么都不必装**。Obsidian 是可选外壳，纯 Markdown 零迁移打开 |
| 能换机快速部署吗？ | ✅ 一条命令（`bash tools/bootstrap.sh` 或 `bootstrap.ps1`），四步、幂等、零硬编码路径 |

## 二、口径修正（2026-11-14）

「96.3% 孤立」是**混算口径**，会误导施工方向：

| | 数量 | 该建知识链吗 |
|---|---|---|
| 知识节点（设定/模板/总览） | 642 | ✅ 是 —— 真缺口 |
| 叙事节点（正文） | 563 | ❌ 否 —— 线性叙事 |

混算不仅数字虚高，更会让人去给 563 篇正文逐章互链。
现已改为**以知识节点为分母**，叙事节点单列观察。
（连带修正 `pkm_check.py` 的 WARN 阈值口径。）

## 三、诊断时未预见、落地中发现的四件事

1. **自引用不收敛** —— MOC 会统计自己的字数，而它的字数随内容变化。
   修法：生成物**不计自身字数**，但**保留其连接贡献**
   （整个排除是过度修正：出链 1266 → 67）。
2. **索引器能解析 ≠ 渲染器能点开** —— MOC 内链接要相对
   **渲染文件自身目录**（`../../`），否则 Obsidian / GitHub 里点不开。
3. **入库产物需要失配检测** —— 新增笔记后产物不会自动跟着变，
   指标会悄悄失真。已加进部署脚本第 6 步。
4. **「提交了」≠「推送了」≠「两端都推了」** —— GitHub 直连在本机
   **间歇性阻断**。已把同步状态做成可校验事实（`sync` 检查器）。

## 四、诊断时的建议 vs 实际做法

诊断报告里写的建议是：「从 `PKM/孤立文档清单.md` 取施工单，按项目分批补连接」。

**这条建议是错的** —— 逐篇补 564 篇设定不现实，且要动设定文件。
实际做法改成了**枢纽节点法**（自动生成项目 MOC），一次到位。
这也是本轮最有价值的一条经验：

> **建连接层时，先问「这件事该由谁做」。**
> 该由机器做的（聚类、编号、交叉引用），别写成人工建议；
> 该由人做的（判断哪两个作品真相关），才写进建议清单。
