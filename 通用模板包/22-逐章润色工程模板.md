# 22 · 逐章润色工程模板（v3.18 新增 · 通用可复用）

> **解决什么**：前面 `05`（文风基准）、`17`（增密）、`18`（程序化）解决的是"怎么写好一章"；本文件解决的是**"怎么把一批已有章节逐章改到位并交付"**——一套可重复执行的润色流水线：诊断 → 取料 → 改写 → 硬校验 → 出件。
> **适用范围**：有原稿、要逐章修订的项目（改稿、润色、连载回炉）。无原稿的新书走 `00` §二 路径 A，本文件整份标 `N/A`。
> **与既有文件的关系**：不替代 `05`（指标口径）与 `17`（增密方法）；本文件给的是**工序与工具**。增密时按 `17` §二/§三 取承重扩写位，判据仍以 `05` §1.1 为准。
> **中性化声明**：本模板不含任何项目专属设定、专名、字数目标（下限由项目 `05` 与试稿实测确定）；示例只示意结构，不可照抄内容。
> **路径登记**：本文件涉及的 `tools/polish/` 六个工具与配置文件均随包分发，路径核验登记见 `14` D-21。

## 一、三条铁律（先立后做）

1. **结构 > 密度 > 语言**。先看这章成不成立，再看够不够厚，最后才看句子。倒着做会舍不得删烂句子，烂结构留下。
2. **不靠标点凑字数**。字数只认汉字（含标题行，不含标点/空格/数字/拉丁字母），口径一次定死；中途改口径，历史交付全部失真。
3. **每一段必须有新信息**。新物、新数、新动作、新规矩、新因果——五者至少其一。删掉一段读者不会少知道一件事，该段就是修饰。

## 二、五步流水线（每一批走一遍）

| 步 | 名称 | 做什么 | 工具/模板 |
|---|---|---|---|
| 0 | 定位 | 从原稿抽一章可读素材（去伪字数形态、并段） | `tools/polish/extract.py` |
| 1 | 诊断 | 按三层诊断表判定本章病灶（结构/密度/语言） | 本文 §三 |
| 2 | 改写 | 按四来源补料、括号三落地、减法清单改 | 本文 §四/§五，`17` §二 |
| 3 | 硬校验 | 字数、括号、引号、半角标点、连续标点——不过不许交 | `tools/polish/count.py` |
| 4 | 体检 | 密度、重复、注水、节奏——出单子逐条看 | `tools/polish/kit.py` |
| 5 | 出件 | 合成 md/txt/docx 交付件，可上传知识库 | `tools/polish/build.py`；单项上传 `tools/polish/upload.sh` |

开工前跑一次 `bash tools/polish/selftest.sh`，四项全绿再动手。

## 三、三层诊断表（第 1 步）

| 层 | 问什么 | 不合格的表现 | 处理 |
|---|---|---|---|
| 结构层 | 这章推进了什么？删掉它后面会不会塌？ | 连续两章都在"他想了很久"；高潮靠巧合；伏笔无回收 | 并章、补章、调序 |
| 密度层 | 每一段有没有新信息？ | 一段重复上一段的意思；两段同义 | 换料（§四） |
| 语言层 | 句子是否有实物垫底？ | 形容词成串；判断句多；"他感到""他知道" | 减法（§五） |

**本章推进了什么**：一句话，不许用形容词；连续三章答案雷同 = 注水信号，回 `02` L4 重排。
**本章的钩子**：以下三类一章至少一个——物（一件东西出现或少了）、数（一个数对不上）、话（一句没说完的话）。

## 四、密度层：括号三落地 + 四来源（第 2 步）

### 4.1 括号三落地

原稿"一行一括号"是常见伪字数来源：括号里塞解释、感叹、判断，删掉不影响情节。每一处括号必须落到三处之一：

| 落法 | 做法 | 示意 |
|---|---|---|
| 并入前句 | 括号里的意思压进前句谓语 | （他听见了。）→ 他听见了，但没抬头。 |
| 独立成段 | 意思够重，单独一段靠空行给重量 | （两个字是：我等。）→ 两个字。／我等。 |
| 化为动作 | 心理判断换成身体或手的动作 | （他很慌。）→ 他把墨在指头上搓开，搓了三下才落笔。 |

**判定**：删掉这段读者会不会少知道一件事？会 → 留并按上法重写；不会 → 删。

### 4.2 四来源（补料不加形容词）

字数不够或发稀，从四个来源补，不要加感慨：

| 来源 | 问什么 | 配比参考 |
|---|---|---|
| 工序（怎么做） | 谁做？用什么？几步？哪步最易坏？坏了怎么补？ | ~40% |
| 账目（值多少） | 一天几个？一年几次？折成钱/饭是多少？ | ~20% |
| 履历（从哪来） | 最痛的一次？最会的一件事？身上哪三样是自己的？ | ~20% |
| 规矩与例外 | 规矩几条？例外谁批？批了记在哪？不批会怎样？ | ~20% |

配比是经验值：全是规矩会变成法条，全是履历会变成回忆录。与 `17` §三的"承重扩写位"配合：四来源给料，承重判据决定是否留下。

## 五、语言层：减法清单（第 2 步末）

按顺序删，删到不能再删：

1. 删判断——"他知道""他明白""这说明"，改成动作或直接给事实。
2. 删形容词串——两处以上叠在一处，只留最硬的一个。
3. 删虚词——缓缓、淡淡、轻轻、微微、仿佛、似乎、某种、一丝、不禁（`kit.py` 会统计高频）。
4. 删解释——读者能自己补的一律不写；补不了说明前面没铺好，回去补铺。
5. 删同义复句——意思相同的两句留短的。

**留下的是**：名词、动词、数字、直接引语。四条红线：不写"他感到"、不写"这说明"、不用"很多年之后"替读者总结、不用形容词给人物定性。

## 六、字数与格式口径（第 3 步硬校验）

> 汉字数 = 全文 Unicode 汉字（含章节标题行），不含标点、空格、数字、拉丁字母。

| 项 | 标准 | 检查 |
|---|---|---|
| 汉字下限 | 按项目 `05` 与试稿实测定，本模板不预设数字 | `count.py --min` |
| 全角括号 | 0 个 | `count.py` |
| 全角引号 | 前后配对 | `count.py` |
| 半角标点 | 0 处（数字小数点除外） | `count.py` |
| 连续标点 | 不允许 `，，` `。。` `！！` | `count.py` |
| 段落 | 一段一意；单句成段是重型武器，一章 ≤15 处 | `kit.py` |

标点用法遵循 GB/T 15834—2011（见 `05` 相关节）。计数只认 `count.py`——不要用文字处理软件的字数统计，口径不同。

## 七、密度公式与出件规范

**密度 = 新增信息量 ÷ 字数**。一"信息" = 一样新物 / 一个新数 / 一个新动作 / 一条新规矩 / 一个新因果。参考阈值：3000 字的章信息量低于 60 条就是稀（阈值随项目体量调整，非硬指标）。连续三段没有新信息，删中间那段。

**草稿命名**： drafts/chNN.md（UTF-8，一章一文件，首行「第N章 标题」）。
**交付件命名**：`<书名>-第X至Y章-润色稿.md / .txt / .docx`（单章不带"至"）。
**出件命令**：`python3 tools/polish/build.py --start X --end Y`；加 `--upload` 上传知识库（目标库由项目配置指定）。
**不做**：整卷合并版——按批读更好定位。

## 八、工具清单（本包自带，位于 tools/polish/）

| 工具 | 作用 | 依赖 |
|---|---|---|
| `extract.py` | 取料：原稿 → 可读素材（去括号、并段）；`--scan` 看目录、`--raw` 看原貌 | Python 3.8+ |
| `count.py` | 硬校验：字数/括号/引号/半角标点/连续标点（唯一计数口径） | Python 3.8+ |
| `kit.py` | 体检：密度/重复/注水/节奏，只出单子不判对错 | Python 3.8+ |
| `build.py` | 出件：合成 md/txt/docx，校验通过后可选上传 | Python 3.8+ + python-docx |
| `upload.sh` | 单文件上传（上传脚本路径由项目环境提供） | Bash + 项目环境 |
| `selftest.sh` | 自检：依赖与工具可用性，四项全绿再开工 | Bash + Python 3.8+ |

脚本为通用骨架：配置从各脚本同目录的 `config.json` 读取（书名、原稿目录、草稿目录、输出目录、字数下限）；换项目只改配置，代码不动。
